## 1. 요약

패치의 대부분은 버그 수정이 아니었다. **처음에 적어두지 않은 전제 조건**을 운영하면서 하나씩 발견한 결과였다.

| 빠져 있던 전제 | 그 결과 생긴 패치 |
|---|---|
| Gemini 무료 키 한도(분당 5회, 일일 한도) | 대기 2초→20초, PR 봇 트리거 축소, 10-13 분석 9/10 실패 |
| 러너는 UTC, 독자는 KST | cron 주석 오류, 6일 누락·5회 덮어쓰기, 실행의 61%가 어제 날짜로 표시 |
| 독자는 나 1명, 아침에 폰으로 읽음 | 인덱스 표, 제목 단축, 모바일 가독성, 퀴즈 주제 교체 |
| 메일 한 줄에 들어가는 글자 수 | 프롬프트 분량 5회 수정, 지금도 85% 초과 |
| LLM 응답은 비거나 막히거나 형식이 깨진다 | 안전 필터 예외, KeyError, 문자열 split 파싱 |
| 사람과 봇이 같은 main에 push한다 | push 방식 5회 변경, 지금도 `--force` |

이 전제를 적어둔 문서가 지금도 없다. 그래서 새 기능(PR 리뷰 봇, NotebookLM)을 만들 때마다 같은 제약을 처음부터 다시 겪었다.

## 3. 실측: 아직 남아 있는 문제

### 3-1. 글자 수 지시는 프롬프트로 해결되지 않는다

`927a133` 이후(10-14 ~ 11-22) 리포트에 실린 문장의 길이를 셌다.

| 항목 | 표본 | 요청 범위 안 | 상한 초과 | 메일에서 "…"로 잘림 |
|---|---|---|---|---|
| Summary (55~60자, 표시 상한 75자) | 342 | 52 (15%) | 290 (85%) | **114 (33%)** |
| WhyTrending (65~70자, 표시 상한 90자) | 349 | 58 (17%) | 290 (83%) | 31 (9%) |

- 중앙값은 Summary 71자, WhyTrending 79자다. 최대는 130자였다.
- LLM은 한글 글자 수를 세지 못한다. **코드에서 검사하고, 넘으면 다시 요청하거나 단어 경계에서 잘라야 한다.**

### 3-2. UTC 날짜

- 스케줄은 22:13 UTC(KST 07:13)이지만, GitHub cron이 밀려 실제 실행은 1~4시간 늦다.
- 날짜는 `datetime.now()`(러너 = UTC)로 계산한다. 그래서 00:00 UTC 전에 끝난 실행은 **KST 기준 어제 날짜**로 찍힌다.
- 03-26 이후 실행 243회 중 **148회(61%)가 어제 날짜**로 파일명·메일 제목·NotebookLM 제목이 붙었다.
- 실행 시각이 00:00 UTC를 넘나들던 날에는 6일치가 빠지고(06-02, 06-15, 06-18, 08-06, 08-26, 09-07) 같은 날짜로 5번 덮어써졌다(06-04, 06-16, 06-19, 08-07, 09-06).
- 10-14 이후 39회는 모두 00:00 UTC 뒤에 돌아서 지금은 날짜가 맞다. 하지만 **cron 지연에 기대어 우연히 맞는 상태**다.

### 3-3. 설명 없는 저장소

- GitHub 설명이 비어 있으면 AI를 부르지 않고 "(원본) 상세 설명이 제공되지 않은 프로젝트입니다"를 넣는다.
- 239일 중 **46일**에 이런 저장소가 하나 이상 있었다. README 앞부분을 입력으로 쓰면 대부분 분석할 수 있다.

### 3-4. 봇의 force push

- `_python-report.yml`이 `if: always()` + `git push --force origin main`으로 끝난다.
- 같은 시각에 사람이 push하면 그 커밋이 사라질 수 있다.
- 스케줄 실행과 수동 실행이 겹쳐도 막는 `concurrency` 설정이 없다.

## 4. 아키텍처 관점

> 좋은 아키텍처의 가치는 "돌아간다"에서 드러나지 않는다. ① 반복 개발을 줄이고, ② 결함을 빨리 분석·조치하게 하고, ③ 새 요구사항이 기존 코드에 미치는 영향을 줄이는 데서 드러난다. 즉 개발·운영 자원을 얼마나 효율적으로 쓰게 하는지라는 경제적 관점으로 평가해야 한다.

### 구조 현황

- `trending.py` 한 파일(607줄, 함수 16개)에 크롤링, AI 분석, 이력 비교, 렌더링 3종, 메일, NotebookLM이 모두 들어 있다.
- 사람이 작업한 커밋 36개 중 **18개(50%)**가 이 파일을 고쳤다.
- 테스트 0개, dry-run 모드 없음. 결과는 실제 메일을 받아 봐야 안다.

### ① 반복 개발 — 같은 문제를 두 번 풀었다

- LLM 호출이 `trending.py`와 `scripts/pr_review.py`에 따로 구현돼 있다. 모델명(`802cc3e`), 안전 필터(`60ac80c`), 무료 한도(`c8490c0`)를 PR 봇에서 다시 고쳤다.
- push 방식은 5번 바뀌었다. 산출물을 어디에, 누가 쓰는지를 설계에서 정하지 않았기 때문이다.
- 반례로 `c74f50b`(재사용 워크플로우)는 경계를 그었더니 반복이 사라졌다. 같은 원칙을 Python 쪽에도 적용하면 된다.

### ② 결함 분석 속도 — 실패가 보이지 않았다

- 메일 실패는 `6b5befb` 전까지 성공과 같은 경로로 흘렀다.
- AI 분석 실패는 리포트에 "오류가 발생했습니다"만 남는다. 원인(예외 메시지)은 90일 뒤 지워지는 Actions 로그에만 있다. 그래서 10-13에 9/10이 실패한 원인을 지금 산출물만으로는 확인할 수 없다.
- 날짜 누락·덮어쓰기 11건이 몇 달 동안 발견되지 않았다. 출력 검증이 없기 때문이다.

### ③ 변경 영향 — 결정 하나가 여러 곳에 흩어져 있다

| 결정 | 흩어진 곳 | 대가 |
|---|---|---|
| 오늘 날짜 | `datetime.now()` 8곳 | 시간대를 고치려면 8곳을 모두 고쳐야 함 |
| 요약 표시 상한 | `short(item…)` 4곳 | `598f6ff`, `927a133`이 매번 4곳 수정 |
| 리포트 제목 | 4곳 (h1, 텍스트, 메일 제목, 노트북명) | `2449adc`가 3곳 수정 |

### 5-2. LLM 프롬프트에 있었어야 할 것

첫 프롬프트(`23ba4bd`)는 "Summary 1~2줄, UseCase 2~3줄"뿐이었다. 빠져 있던 것은 다음과 같다.

1. **독자와 용도:** "개발자 뉴스레터 에디터"(`8ecbc6b`에서 추가), 어디에 표시되는지
2. **금지 사항:** 일반론 금지(`8ecbc6b`에서 추가). 입력에 없는 수치를 지어내지 말 것(아직 없음)
3. **출력 계약:** 문자열 split이 아니라 JSON 스키마로 받는다. 테마 분류는 이미 JSON인데 저장소 분석만 split이다
4. **길이는 프롬프트가 아니라 코드가 보장:** 프롬프트에는 목표만 주고, 코드가 검사 → 1회 재요청 → 단어 경계 자르기
5. **입력 보강:** 설명이 비면 README 앞부분을 넣는다

### 5-3. AI 코딩 도구에게 줄 프롬프트(작업 지시)에 있었어야 할 것

`a812e52` 이후 커밋은 대부분 AI 코딩 도구로 만들었다. 매 세션이 제약을 모른 채 시작했다.

- 저장소에 `CLAUDE.md`가 없어서 세션마다 무료 한도, KST, 모바일, force push 위험을 다시 발견했다.
- 작업 지시에 "완료 기준"이 없었다. 예를 들어 "요약 60자"를 지시했지만 "리포트 N개에서 길이를 세어 확인"은 요구하지 않았다. 그래서 85% 초과가 지금까지 남았다.
- 지시가 "이걸 바꿔줘" 단위라서, 같은 결정이 흩어진 다른 곳(렌더러 4곳, 날짜 8곳)은 매번 사람이 짚어야 했다.

## 6. 회고 정리 (KPT)

### Keep
- 리포트 저장 → 메일 순서와, 메일 실패에도 아카이빙하는 구조(`6b5befb`)
- 재사용 워크플로우 분리(`c74f50b`): 경계를 그어 반복을 없앤 좋은 사례
- 실패해도 리포트를 막지 않는 폴백(테마 분류 실패 시 언어별, 오디오 실패 무시)
- 커밋 메시지에 변경 이유를 남긴 것(`7ba6b96`, `aad9778`). 이번 회고가 가능했던 이유

### Problem
- 전제 조건(한도, 시간대, 독자, 표시 공간)을 적지 않고 시작했다
- LLM 출력을 프롬프트로만 통제하려 했다
- 실패가 결과물에 드러나지 않았다
- 결정 하나가 여러 곳에 흩어져 있다
- 실험할 곳이 운영뿐이었다
- 파일 통째 교체로 기존 기능이 사라졌다(`345af0d`, `75f3971`)

### Try
1. **제약을 문서로 남긴다:** 저장소 루트 `CLAUDE.md`. 새 기능을 만들기 전에 읽는다
2. **결정은 한 곳에:** KST `NOW` 1회 계산, 모델명·표시 상한·제목은 상수로
3. **LLM 호출 경계 하나:** `call_llm()`이 JSON 파싱, 길이 검증, 1회 재요청, 실패 사유 반환까지 맡고 `pr_review.py`와 공유
4. **실패는 산출물에:** 리포트 상단 상태 줄(AI 성공 n/10, 실패 사유). 기준을 넘으면 워크플로우 실패
5. **실험은 운영 밖에서:** `--dry-run`(메일·커밋 없음, 저장된 샘플 사용)과 스모크 테스트 1개
6. **push 안전:** force push 제거, `concurrency` 추가
7. **완료 기준을 숫자로:** "N일치 리포트에서 범위 준수율 X% 이상"처럼 측정 가능하게 지시한다

> 규모에 맞춘다: 607줄짜리 1인 도구에 패키지 분할이나 레이어드 구조는 과하다. 원칙은 **결정은 한 곳에, 실패는 눈에 보이게, 실험은 운영 밖에서** 세 가지면 충분하다.
